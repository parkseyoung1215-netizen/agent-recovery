## 실험 6 - "이미 처리됐는지" 조회 기능이 없는 서비스 (중복 방지 키만 지원)

메일 50건 중 33번째 1번 503. 조회 기능 없음. n8n Retry = 노드 전체 다시 보내기를 흉내 냄.

| 방법 | 총 발송 | 받은 사람 | 중복 | 결과 |
|---|---|---|---|---|
| 키 없음 → n8n Retry | 99통 | 50명 | 49건 | 성공으로 끝남 |
| 키 없음 → recover.py 방식 | 49통 | 49명 | 0건 | 조회 불가 50건 → 하나도 안 보내고 사람에게 넘김 (1명 누락) |
| 처음부터 키 → n8n Retry | 50통 | 50명 | 0건 | 서버가 49건을 '이미 받은 요청'으로 무시 |

- 조회 기능이 없으면 실패한 "다음에" 고치는 방법(recover.py)은 안전하지만 일을 끝내지 못함.
- 실패하기 "전에" 중복 방지 키를 붙여두면 n8n 기본 Retry만으로도 중복 0, 누락 0.
- 즉 조회 기능이 없는 서비스에서는 예방(check.py가 키를 권하는 것)이 유일하게 완전한 해결책.
- 클라우드에서 n8n 동작을 흉내 내서 돌린 결과. 실제 n8n에서는 아직 안 돌림.

## v0.3 - n8n 커뮤니티 2차 피드백 반영 (sameday, kartike, Clearwork Desk)

sameday가 391324a 버전을 직접 돌려보고 찾은 버그:
1. 조회 반영이 대기 시간보다 늦으면 다시 보내서 서버에 2번 기록되는데도 "중복 0건"이라고 출력 (확인 없이 항상 찍히는 문구였음)
2. 조회 응답이 {} 이면 "없음"으로 보고 다시 보냄, {"exists":"false"}(글자)면 "있음"으로 봄

고친 것:
- "중복 0건" 문구 삭제. 보낸 요청 수만 보고하고, 실제 중복은 상대 서비스 기록으로 확인하라고 안내
- 조회 응답이 진짜 true/false가 아니면 "확인 불가" (사람에게)
- 자동으로 다시 보내는 건 두 경우만: (a) 바로 반영되는(strong) 조회가 "없음"을 확인 (타임아웃이면 대기 후), (b) 처음부터 같은 중복 방지 키를 붙인 경우. 늦게 반영되는(eventual) 서비스는 기다린 뒤에도 "없음"을 믿지 않고 사람에게 넘김
- 보내기 전에 기록 + 원자적 잠금 (kartike: 체크포인트는 보내기 전에 / Clearwork Desk: 두 작업자 동시 처리 방지). 보낸 뒤 기록 전에 멈추면 'sending' 기록이 남아 사람이 확인
- 회귀 테스트 13개 (tests/test_rules.py), 모두 통과. 그중 하나는 일부러 가정이 깨지는 경우(늦게 반영되는 서비스를 strong으로 잘못 설정하면 중복 1건)를 보여줌

실험 7 다시 실행 (조회 8초 늦게 반영):
| 방식 | customer10 (503) | customer20 (타임아웃, 실제로는 보냄) | 총 발송 | 중복 |
|---|---|---|---|---|

| v0.3 | 확인 대기 → 확인 불가 (사람에게) | 확인 대기 → 이미 처리됨 | 49통 | 0건 |

- v0.3은 중복은 안 만들지만 customer10 1건은 자동으로 끝내지 못하고 사람에게 넘김. 안전 대신 완결성을 포기한 것.

## 실패 주입 테스트 (ar.py chaos, 실제 n8n 2.46.6)

같은 메일 50건 워크플로를 세 가지 설정으로 만들고, HTTP 요청이 진짜 서비스 대신 시험용 가짜 목적지(127.0.0.1:8200)로 가게 바꿔서 실행. 33번째 쓰기 요청에 503을 넣음. 진짜로 나간 메일은 없음.

| 워크플로 | 쓰기 요청 | 기록된 항목 | 판정 | n8n 표시 |
|---|---|---|---|---|
| A 재시도 없음 | 50 | 49 | 실패: 누락 1건 (customer34) | 실패 |
| B Retry On Fail (3번) | 100 | 50 | 실패: 중복 49건 | 성공 |
| C Retry On Fail + Idempotency-Key 헤더 | 100 | 50 | 통과: 중복 방지된 재시도 49건 | 성공 |

- B는 n8n에 성공으로 표시되지만 테스트는 중복 49건으로 실패시킴. 배포 전에 잡을 수 있음.
- C가 통과하는 건 가짜 목적지가 같은 키를 무시해 주기 때문. 실제 서비스가 Idempotency-Key를 지원해야 같은 결과가 나옴.
- 이번엔 실패한 게 customer34였음 (동시에 보내서 도착 순서가 매번 다름).
- 아이디어: n8n 커뮤니티 ccch713 ("실패를 넣는 테스트를 워크플로를 바꿀 때마다 돌린다")
